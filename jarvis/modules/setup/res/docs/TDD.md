# TDD

## 원칙

1. 작업을 다음으로 분류.
   1. 테스트가 필요없음. -> 바로 구현 + 간단한 실측 검증 후 완료 보고.
   2. 테스트가 필요.
2. 테스트가 필요한 경우 다음으로 분류.
   1. 스펙 변경이 요청됨. -> 변경된 스펙으로 해당 기능에 대한 테스트 수정, RED 확인 후 구현 진행.
   2. 새로운 기능 추가 요청이지만 중복 요청임. -> 스펙 변경이 존재하는 경우 1번으로 진행
   3. 정말로 새로운 기능 추가 요청임. -> RED 테스트 작성 후 구현 진행.
   4. GREEN까지 구현 진행
   5. 적대적 리뷰 진행
      1. 테스트 리스트 커버리지가 기능을 단언할 정도로 충분한지 리뷰
      2. 테스트 리스트 -> 테스트 코드 컴파일 잘 되었는지 리뷰
      3. `LOW` 이슈만 생길 때 까지 진행
   6. 뮤테이션 테스트 진행

## 테스트 작성

- 케이스 하나에 테스트 하나. 이름은 `TEST_SPEC.md`의 조건절을 그대로 쓴다.
- 각 테스트는 고유한 ID를 가진다. 이는 `TEST_SPEC.md`의 케이스 ID와 동기화된다.
- 테스트 코드에는 어떤 케이스를 커버하는지 상세한 주석이 작성된다.
- 구현 의존적인 것이 아닌 행동 기반적으로 작성되어야 한다.
- 실제 사용자 홈·시크릿·에디터 설정을 대상으로 삼지 않는다. 임시 디렉터리를 쓴다.

## 적대적 리뷰

> 작성자와 다른 컨텍스트에서, 작성자와 같거나 더 높은 등급의 모델로 돌린다.

- 심각도 분류:
  - `CRITICAL`(데이터 손실·보안등)
  - `HIGH`(계약 위반·오동작등)
  - `MEDIUM`(누락된 케이스등)
  - `LOW`(가독성등).
- `CRITICAL`·`HIGH`, `MEDIUM` 는 고치기 전에는 완료가 아니다.
